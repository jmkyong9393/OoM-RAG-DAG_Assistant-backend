# 취약점 제보·Open API 운영 지침

## 제1장 총칙

제1조(목적과 적용 범위)
① 이 지침은 회사 서비스의 보안 취약점 제보 접수와 처리, 판매자 Open API 인증키와 호출 한도 관리, API 점검·장애 공지 기준을 정해 회원 정보와 서비스를 안전하게 지키는 것을 목적으로 한다.
② 이 지침은 다음에 적용한다.
1. 회사가 운영하는 온라인몰(직매입·입점 판매자 상품), 해외직구 서비스, 오프라인 매장과 관련된 웹·앱 서비스와 시스템
2. 회사 Open API를 이용하는 입점 판매자와 연동 솔루션 업체 등 개발자센터 파트너
3. 회사 서비스의 취약점을 찾아 제보하는 외부 연구자
③ 취약점 제보 처리 기준의 요약은 별표 1, 판매자 API 인증과 호출 한도 기준은 별표 2와 같다.

## 제2장 취약점 제보 대상

제2조(제보 창구)
① 외부 연구자는 회사가 외부 버그바운티 플랫폼에 개설한 프로그램으로 취약점을 제보한다.
② 민감한 세부 내용은 제보 건 안에서 회사가 따로 알려 주는 안전한 경로로 넘긴다.
③ 취약점에 관한 소통은 제보 건 안에서만 하며, 정책이나 적용 범위에 관한 질문은 회사가 지정한 별도 이메일로 받는다.
④ 다만 사전 검증이나 처리 진행 상황을 고객센터에 묻는 연구자는 프로그램 자격을 잃거나 차단될 수 있다.

제3조(제보 대상 취약점)
① 제보 대상은 악용 가능성이 있고 보안 영향이 큰 취약점으로 한정한다.
② 대표 유형은 다음과 같다.
1. 인증 우회와 권한 없는 민감 데이터 접근
2. 다른 회원 정보의 변조
3. 원격 코드 실행
4. OWASP Top 10에 드는 취약점
5. 시스템의 무결성·기밀성·가용성을 직접 해치는 문제
③ 회사는 관리자 화면, 회원 계정, 판매자·파트너 화면 같은 핵심 자산과 그 밖의 비핵심 자산을 목록으로 공개하며, 목록에 없는 자산은 대상에서 뺀다.
④ 다만 목록에 없는 회사 하위 도메인을 테스트하려면 제보 전에 운영팀에 먼저 문의한다.

제4조(제외 범위)
① 서비스 거부(DoS·DDoS) 공격과 사회공학 기법은 제보 대상에서 제외한다.
② 다음 사항도 제보 대상에서 제외한다.
1. 물리적 보안 침해, 스팸 발송, 제3자 애플리케이션 공격
2. 영향이 작은 CSRF, 보안 헤더 누락, 오류 메시지·버전 정보 노출, Self-XSS
3. 이미 알려진 취약점과 탈옥·루팅 기기나 중간자 공격이 있어야 하는 경우
4. 화면 오류, 링크 작동 불량, 서비스 장애 같은 기능 버그
③ 다만 입점 판매자의 상호·대표자명·사업장 주소는 개인정보로 보지 않으며, 설계상 공개되는 CDN 파일의 노출도 취약점으로 보지 않는다.

제5조(보고서 작성)
① 연구자는 취약점을 확인하는 즉시 제보하고, 보고서에는 문제를 재현할 수 있는 정보를 담는다.
② 보고서에는 다음을 적는다.
1. 영향받는 시스템의 IP 주소나 URL
2. 연구자 본인의 IP 주소
3. 취약점 설명
③ 회사는 복잡한 건이면 추가 정보를 요청할 수 있다.
④ 한 사건을 여러 건으로 쪼개 제보하지 않으며, 웹·iOS·안드로이드 등 여러 서비스에서 같은 수정으로 고쳐지는 문제는 한 건으로 보아 처음 들어온 유효 제보에만 포상한다.
⑤ 다만 패치된 지 1개월이 안 된 제로데이 취약점 제보는 사안별로 판단해 받는다.

## 제3장 테스트 행위 기준

제6조(테스트 계정과 대상)
① 테스트는 연구자 본인이 소유하거나 직접 만든 계정·스토어에서만 하고, 다른 회원의 계정이나 데이터를 대상으로 삼지 않는다.
② 연구자는 외부 버그바운티 플랫폼이 부여한 별칭 이메일로 회원 가입하고, 요청 헤더에 연구자 식별 정보를 넣는다.
③ 회사는 테스트 계정을 따로 제공하지 않으므로, 인증에 휴대전화 번호가 필요하면 연구자가 직접 마련한다.
④ 다만 계정 소유자의 명시적 허락을 받은 경우에는 그 계정으로 테스트할 수 있다.

제7조(금지 행위)
① 개인정보 침해, 데이터 파괴, 서비스 장애나 성능 저하를 일으키는 테스트는 하지 않는다.
② 취약점 입증에 필요한 범위를 넘어 데이터를 내려받거나, 본인 소유가 아닌 데이터를 건드리거나 바꾸거나, 법을 어기는 테스트를 해서는 안 된다.
③ 자동화된 스캐닝 도구는 쓸 수 없으며, 이를 어기면 IP 차단이나 관계 당국 신고로 이어질 수 있다.
④ 회사의 AI(LLM) 시스템을 테스트할 때는 침투적 행위, 데이터 오염, 무단 삭제를 하지 않는다.
⑤ 개발자센터 파트너도 취약점 스캐닝·불법 침입·악성프로그램 유포와 대량 트래픽으로 정상 서비스를 방해하는 행위를 해서는 안 된다.

제8조(공개 제한과 데이터 처리)
① 취약점이 해결되기 전에는 그 내용을 외부에 공개하지 않으며, 공개는 외부 버그바운티 플랫폼의 공개 지침에 따른다.
② 연구 과정에서 얻은 민감한 데이터는 삭제한다.
③ 다만 해결이 끝난 취약점이라도 회사의 명시적 동의 없이는 프로그램 밖에서 논의하지 않는다.

## 제4장 제보 처리와 포상

제9조(회신과 처리 기간)
① 회사는 제보를 받은 날부터 3영업일 이내에 평가 결과와 예상 해결 일정을 연구자에게 알린다.
② 해결 일정에 어려움이 생기면 해결될 때까지 진행 상황을 계속 알린다.
③ 연구자가 보고서에 남긴 질문에 회사가 2주 동안 답하지 않으면, 연구자는 외부 버그바운티 플랫폼에 중재를 요청할 수 있다.
④ 다만 회사 Open API로 외부 개발자가 만든 연동 앱의 취약점은 먼저 그 앱 개발자에게 알리고, 개발자가 1주 안에 응답하지 않을 때만 회사에 연락한다.

제10조(포상)
① 회사는 심각도 점수에 따라 포상금을 정하며, 최대 2억 원까지 지급한다.
② 회사는 분류(triage)를 마친 뒤 1주 안에 포상금을 지급하도록 노력한다.
③ 이전에 보고되지 않은 취약점이면 그 취약점을 공개할 때 연구자의 공로를 인정한다.
④ 회사에 영향을 주는 공급업체·제3자 취약점의 포상은 회사 재량으로 정한다.
⑤ 다만 이 지침의 규칙을 지키지 않은 제보에는 포상하지 않고, 제9조 제4항의 연동 앱 취약점은 포상 없이 참고 건으로 닫는다.

제11조(선의 연구자 보호)
① 회사는 이 지침을 지키고 선의로 행동한 연구자에게 해당 제보와 관련해 법적 조치를 하지 않는다.
② 회사는 외부 버그바운티 플랫폼의 표준 세이프 하버 조항을 적용한다.
③ 다만 이 지침의 규칙을 어긴 연구자는 프로그램 자격을 잃으며, 제1항의 보호도 받지 못한다.

## 제5장 API 인증키 관리

제12조(인증키 발급 자격과 신청)
① 판매자 Open API 인증키는 회사 온라인몰에 입점 판매자로 등록한 사업자만 받을 수 있다.
② 판매자는 판매자 관리 화면에서 약관에 동의하면 Access Key와 Secret Key로 이루어진 Open API 키를 바로 발급받는다.
③ 다만 접근 권한 반영에는 24시간 넘게 걸릴 수 있고, 회사는 별도 테스트 환경을 제공하지 않는다.
④ 연동 솔루션 업체 등 개발자센터 파트너는 개발자센터에 앱 등록을 신청하며, 개발 범위·판매자 ID·사이트 URL·최근 3개월 판매량·개발 기간에 회사 소개와 연동할 판매자 수를 더해 적는다. 등록되면 Client ID와 Client Secret을 함께 발급한다.
⑤ 회사는 내부 자원 한도와 검색 성능·서비스 안정성을 이유로 신청을 거절할 수 있다.

제13조(인증키·토큰 유효기간과 재발급)
① Open API 키의 유효기간은 180일이며, 만료되면 인증이 실패하므로 재발급해야 한다. 회사는 만료 2주 전과 1주 전에 등록된 판매자 이메일로 안내한다.
② 재발급 버튼은 만료 14일 전부터 열리며, 그보다 일찍 바꾸려면 기존 키를 삭제한 뒤 새로 발급한다. 재발급과 연동 정보 수정은 30분 안에 반영된다.
③ 파트너 앱의 Access Token은 2시간, Refresh Token은 14일 동안 유효하며, 갱신하면 새 Refresh Token이 나오고 이전 것은 자동 폐기된다.
④ 다만 인가 코드는 1분 동안 한 번만 쓸 수 있고, 토큰은 호출할 때마다 새로 받지 말고 저장해 재사용한다.

제14조(접속 IP와 요청 규격)
① 판매자는 키를 발급받을 때 연동할 PC나 서버의 IP를 10개까지 등록하며, 연동 정보는 주 10회까지 고칠 수 있다.
② 회사는 요청마다 키 보유자, 허용 서버 IP, 위변조 여부와 API별 권한을 확인하며, 하나라도 통과하지 못하면 API에 닿기 전에 HTTP 401로 거절한다.
③ 파트너 앱이 토큰 발급 요청 규격(본문 전달, form-urlencoded 형식, grant_type 포함 등)을 지키지 않으면, 회사는 이전 사용량과 관계없이 그 앱의 호출을 시간당 1회로 제한한다.
④ 다만 제한 여부는 전날 토큰 요청이 모두 규격을 지켰는지로 매일 다시 정하므로, 규격을 맞추면 이르면 다음 날 아침 풀리지만 비표준 요청이 한 번만 있어도 제한이 이어질 수 있다.

제15조(인증키 유출 방지)
① Access Key·Secret Key, Client Secret, 만료 전 토큰은 외부에 노출하지 않는다.
② 온라인 문의나 기술지원 게시판에는 키·시크릿, 만료 전 토큰, 개인·결제 정보를 적지 않는다. 기술지원 게시판 글은 바로 공개되고 검색에도 걸리므로, 회사는 이런 정보가 담긴 글을 통보 없이 지운다.
③ 판매자와 파트너는 부여받은 인증 정보가 새지 않게 관리할 책임을 지며, 회사의 서면 동의 없이 제3자에게 양도·대여하거나 공유하지 않는다.
④ Client Secret은 소스 코드에 적지 말고 환경변수로 불러오며, .env 파일은 저장소에서 뺀다.

제16조(인증키 유출 시 조치)
① 시크릿이나 유효한 토큰이 공개되면 회사는 보호를 위해 해당 애플리케이션 시크릿을 강제로 재설정할 수 있다.
② 노출이 생기면 판매자·파트너는 게시글의 민감 정보와 수정 이력까지 지우고, 개발자센터의 애플리케이션 화면에서 새 시크릿을 확인해 연동 프로그램에 반영한다.
③ 파트너는 이상 징후나 침해사고가 생기면 즉시 회사에 알리고, 비상시 연락이 닿는 최신 연락망을 유지한다.
④ 다만 토큰 폐기 API로 Access Token을 폐기하면 연결된 Refresh Token도 함께 폐기된다.

## 제6장 호출 한도와 제재

제17조(호출 한도 기준)
① 호출 한도는 판매자나 애플리케이션 단위로 매긴다.
② 판매자 Open API 키는 업체코드별로 초당 10회를 넘는 호출을 막으며, 상품 등록·수정과 수량·가격·판매 상태 변경 API가 대상이다.
③ 다만 주문 조회 API는 업체코드별로 5초에 1회, 상품 목록 조회 API는 분당 20회(한 번에 최대 500개)로 제한한다.
④ 파트너 앱의 Admin API는 액세스 토큰 단위로 세며, 10분마다 호출 3,000회와 처리 시간 600초의 총량 한도를 두고, 용량 40에 초당 2개씩 빠지는 버킷으로 순간 유량을 제한한다.

제18조(한도 초과 시 응답)
① 한도를 넘은 요청은 처리하지 않고 HTTP 429(Too Many Requests)로 돌려준다.
② 파트너 앱에는 X-Api-Call-Limit 응답 헤더로 사용량과 용량을 함께 알려 준다.
③ 다만 주문 조회 한도를 넘으면 결과 코드 3000과 빈 데이터를, 상품 목록 조회 한도를 넘으면 분당 20회 초과 안내와 1분 뒤 다시 조회하라는 메시지를 돌려준다.
④ 네트워크·처리·캐시 지연 때문에 한도 판정에는 밀리초에서 초 단위의 오차가 생길 수 있다.

제19조(차단·해제와 제재)
① 한도를 넘는 호출이 반복되면 즉시 차단하며, 호출을 한도 안으로 줄이면 수 분에서 수십 분 안에 차단을 푼다.
② 다만 과도한 호출이 계속되면 자동으로 영구 차단될 수 있다.
③ 파트너가 제7조 제5항의 금지 행위를 포함해 개발자센터 약관 의무를 어기면, 회사는 사전 통지 뒤 이용을 제한하거나 앱을 삭제할 수 있고, 시정 요구 뒤 7일 안에 고치지 않으면 계약을 해지할 수 있다.
④ 토큰 발급 규격 위반에 따른 시간당 1회 제한과 해제는 제14조 제3항·제4항에 따른다.

제20조(한도 변경과 호출 설계)
① 회사는 호출 한도를 바꿀 때 적용 전에 공지하며, 공지 시점은 제22조에 따른다.
② 다만 플랫폼 전체 수용량은 공개하지 않으며, 수용량은 바뀔 수 있다.
③ 판매자·파트너는 HTTP 429를 받으면 1·2·4·8·16초로 간격을 늘려 다시 시도하고, 버킷을 계속 채우는 즉시 재시도는 피한다.
④ 대량 호출 서비스나 일괄 작업은 요청을 큐에 쌓아 요청 사이를 0.5초 이상 띄워 보낸다.

## 제7장 점검·장애 공지

제21조(정기점검과 사전 통지)
① 회사는 Open API를 연중무휴 24시간 제공하는 것을 원칙으로 하되, 정기점검·업그레이드 때는 미리 통지하고 서비스를 임시로 멈출 수 있다.
② 통지는 판매자·파트너가 등록한 이메일·문자·전화로 하며, 여러 대상에게 알릴 때는 개발자센터 공지사항에 7일 이상 게시하는 것으로 개별 통지를 갈음한다.
③ 점검 공지에는 접속 실패·응답 지연·요청 실패와 일부 또는 전체 API의 일시 중단 가능성을 적고, 점검 뒤 상품 변경 반영 여부와 미처리 주문을 확인하도록 안내한다.
④ 다만 점검 일정은 진행 상황에 따라 예고 없이 바뀔 수 있다.

제22조(변경 사항 사전 공지)
① API 사양·호출 한도·보안 설정을 바꿀 때는 적용 전에 개발자센터 공지로 알린다.
② 호출 한도 변경과 API 서버의 TLS 암호 설정 변경·인증서 교체는 적용일보다 6일 이상 앞서 공지한다.
③ 적용일을 미루면 공지를 고쳐 다시 알리고, 판매자 쪽 수정이 필요 없으면 그 사실을 함께 밝힌다.
④ 개발자센터 약관을 바꿀 때는 적용일 7일 전에 공지하고, 회사 정책에 따른 계약 해지는 30일 전에 알린다.
⑤ 다만 판매자·파트너에게 불리한 약관 변경은 30일의 유예 기간을 둔다.

제23조(긴급 중단)
① 긴급 점검, 설비 장애, DDoS 공격 등 개발자센터 약관에 정한 8가지 사유가 생기면 회사는 사전 통지 없이 서비스를 멈출 수 있다.
② 서비스 일부는 사전 통지 없이 바꿀 수 있으나, 서비스 전체를 중단할 때는 미리 통지한다.
③ 다만 이런 사유로 서비스가 멈춰 생긴 파트너의 손해는 회사가 책임지지 않으며, 회사 귀책 장애의 배상은 제25조에 따른다.

제24조(장애 공지 방식)
① 회사는 장애가 난 당일 판매자·파트너가 볼 수 있게 개발자센터 공지사항에 장애 글을 올리고, 제목에 장애 표시와 영향받은 API 그룹·날짜를 붙이며, 복구가 끝나면 제목에 복구 완료를 적는다.
② 장애 공지에는 다음을 담는다.
1. 영향 시간(시작·종료 시각)
2. 영향받은 API 그룹과 기능
3. 오류 증상(HTTP 500·503·504 응답 등)
4. 원인과 관련 공지
5. 정상 응답을 받지 못한 요청의 재확인·재호출 안내
③ 다만 장애 시간 동안 정상 응답을 받지 못한 요청은 판매자·파트너가 직접 다시 확인하거나 다시 호출하고, 판매가와 재고를 점검해야 한다.

제25조(장애 보상)
① 회사 귀책으로 서비스가 4시간 이상 멈추거나 장애가 나면, 회사는 최근 3개월(3개월이 안 되면 그 기간) 수수료의 1일 평균을 24로 나눈 금액에 장애 시간을 곱하고 그 3배를 파트너에게 배상한다.
② 장애 시간은 파트너가 회사에 장애를 알린 때부터 센다.
③ 다만 기대 수익 손실과 무료 서비스 관련 손해는 법에 특별한 규정이 없으면 회사가 책임지지 않는다.
